### Important — P2: reconcile GET wire identity with supported older stored snapshots

**Primary location:** `web/src/live-data.ts:68`. Supporting contract: `worker/src/ingest.ts:76`, `worker/src/index.ts:52`, `worker/tests/core.test.mjs:91` and `web/src/data.ts:174`.

The new browser requires `sha256(JSON.stringify({ source_id, snapshot: entry.snapshot }))` to equal the returned digest. That is correct for newly normalized uploads, but not for all snapshots the existing Worker intentionally supports. `restoreUpload` checks the exact retained canonical bytes, then runs them through today's `parseSnapshot`, and returns the old digest with the newly normalized snapshot. `current` sends that pair unchanged.

The existing compatibility regression provides a concrete case: it removes optional `area_text` from a retained record, hashes those original bytes and requires restoration to preserve that hash. Today's parser adds `area_text: null` back. The GET snapshot therefore contains bytes absent from the hash input, and line 68 rejects it every time. A healthy supported source remains on dated fallback until a new compatible head arrives. This is an integration availability defect, not acceptance of corrupted data; the safe fallback limits its severity but does not complete the contract. The implementer's self-review acknowledges the mismatch without resolving it.

**Fix:** reconcile the producer's GET wire representation and digest while preserving exact stored-byte integrity and existing stored identity. For example, return the integrity-verified original snapshot representation for browser validation, or explicitly distinguish a verified response-projection digest from the stored snapshot ID. Do not weaken browser digest validation or replace immutable retained blobs. Add a focused regression through the actual Worker GET response and browser reader for both the current normalized envelope and the existing legacy optional-field case, plus corrupt/mismatched identity rejection. The current browser fixture normalizes first and therefore cannot expose this incompatibility. Any necessary Worker scope adjustment should be recorded before implementation.
